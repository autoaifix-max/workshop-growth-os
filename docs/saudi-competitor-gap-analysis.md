# تحليل المنافسين والفجوات — Workshop Growth OS
**تاريخ البحث:** 10 أكتوبر 2026  
**السوق الأساسي:** ورش صيانة السيارات المستقلة في السعودية، مع قابلية التوسع خليجيًا.  
**الغرض:** قرارات منتج قابلة للبيع، لا تجميع مزايا تسويقية. الأسعار والمزايا أدناه من صفحات عامة منشورة وقت البحث؛ لم تُختبر المنتجات عمليًا، وأرقام العملاء/الانتشار لم تُعامل كحقائق مستقلة ما لم تتوفر أدلة موثوقة.

## الخلاصة التنفيذية

السوق ليس خاليًا من المنافسة ولا يكفي أن نقدم «إدارة ورشة مع ذكاء اصطناعي». توجد منتجات محلية تجمع أوامر الشغل والمخزون والفوترة والتذكير بالعملاء، وبعضها يسعّر بسعر منخفض جدًا. لذلك لا نوصي بمنافسة السوق على عدد الشاشات أو الادعاء بأن الذكاء الاصطناعي وحده ميزة فريدة.

**الفرصة المقترحة:** أن يكون Workshop Growth OS نظامًا يقيس ويُحسّن نتيجة الورشة، لا مجرد مكان لتسجيل العمليات. نبدأ بثلاثة تمايزات قابلة للاختبار:
1. **مؤشر ربحية وتسرب لكل أمر شغل:** مقارنة قيمة العمل والقطع والتكلفة والوقت الفعلي، مع تنبيهات قابلة للتفسير عن القطع غير المفوترة، تجاوز الوقت، الخصومات والعودة المتكررة.
2. **رحلة موافقة موثقة للعميل:** عرض سعر واضح، قبول/رفض لكل بند، سجل من وافق ومتى، ثم تحديث الحالة برسالة عبر قناة مفعّلة بموافقة العميل. لا تُرسل رسائل آلية قبل بناء التكامل والامتثال.
3. **تهيئة ونقل بيانات سريعة للورشة:** استيراد مضبوط من Excel، قائمة تحقق لتجهيز العملاء والمركبات والخدمات والفنيين، ثم تجربة تشغيل موجهة على أوامر فعلية خلال 7–14 يومًا. هذه ميزة تنفيذ وخدمة وليست ادعاءً بأن الأداة موجودة بالفعل.

**قرار معماري:** لا نبني محرك AI واسعًا الآن. نثبت أولًا جودة بيانات أمر الشغل والتكلفة والموافقة، ثم نضيف مساعدًا يشرح المؤشرات ويقترح خطوات مع بقاء القرار والتنفيذ بيد الإنسان.

### موثق في README الحالي
- Next.js App Router وTypeScript.
- واجهات API للعملاء والمركبات والحجوزات.

- اختبارات تكامل فعلية لعزل ورشتين.
- واجهة العميل للحجز والمتابعة.
- إرسال WhatsApp فعلي مع موافقات وسجل تدقيق.
- القياسات المالية التفصيلية وربحية أمر الشغل.
- مساعد AI مرتبط ببيانات موثوقة وضوابط موافقة.
- الفوترة الإلكترونية السعودية/تكامل ZATCA؛ لا يُسوّق على أنها موجودة قبل تنفيذها والتحقق من المتطلبات الرسمية.

## مواصفات أول 3 تمايزات قابلة للتنفيذ

### DG-01 — لوحة ربحية وتسرب أمر الشغل
**المستخدم:** صاحب الورشة/المدير.  
**المدخلات المطلوبة:** بنود العمل والقطع، سعر البيع، التكلفة المعروفة، الوقت المعياري والفعلي إذا توفر، الخصومات، حالة الأمر.  
**المخرجات:** هامش إجمالي للأمر عندما تتوفر بيانات التكلفة، تنبيه بند منفذ غير مفوتر إذا كان هناك دليل بيانات، فرق الوقت المعياري/الفعلي، وتقرير بالأسباب لا مجرد لون أحمر.  
**ضوابط:** لا تقدّر تكلفة مفقودة بصمت؛ اعرض «بيانات غير مكتملة». لا تُظهر أرقامًا تقديرية كأنها ربح محقق. صلاحيات حسب الورشة.

**اختبارات قبول:**
- لا يظهر هامش ربح إذا كانت تكلفة القطع/العمل ناقصة دون وسم واضح.
- كل رقم في التقرير يمكن تتبعه إلى بنود أمر الشغل.
- لا تستطيع ورشة قراءة مؤشرات ورشة أخرى.
- حالات الإلغاء والخصم والضمان لا تُحتسب مرتين.

### DG-02 — موافقة العميل على بنود عرض السعر
**المستخدم:** مستشار الخدمة والعميل.  
**المخرجات:** نسخة عرض سعر، قرار قبول/رفض لكل بند، الطابع الزمني، صاحب القرار، ونسخة العرض التي تمت الموافقة عليها.  
**ضوابط:** أي تغيير في السعر أو نطاق الإصلاح بعد الموافقة يتطلب موافقة جديدة؛ لا يبدأ تنفيذ بند إضافي بلا موافقة مخولة؛ الرسائل خارج النظام تتطلب قناة مهيأة وموافقة العميل.

**اختبارات قبول:**
- لا يمكن تحويل بند مرفوض إلى «موافق عليه» عبر طلب API غير مخول.
- تعديل العرض بعد الموافقة لا يغيّر سجل الموافقة القديم.
- تكرار الطلب لا ينشئ موافقات مكررة.
- يسجل سجل التدقيق الفاعل والتوقيت والتغيير.

### DG-03 — مسار تهيئة الورشة واستيراد البيانات
**المستخدم:** صاحب الورشة/مسؤول التهيئة.  
**المخرجات:** نموذج CSV/Excel موثق، معاينة قبل الاستيراد، تقرير صفوف مقبولة/مرفوضة وأسبابها، وخطوات إكمال الإعداد.  
**ضوابط:** لا استيراد إلى الإنتاج بلا معاينة وتأكيد؛ لا تخمين لمطابقة لوحة أو هاتف؛ إمكانية إعادة المحاولة دون تكرار السجلات.

**اختبارات قبول:**
- ملف خاطئ يعرض الأخطاء ولا يكتب بيانات جزئية بصمت.
- إعادة استيراد الملف لا تكرر السجلات المتطابقة.
- كل سجل مستورد مربوط بالورشة الصحيحة.
- يمكن تصدير بيانات الورشة عند الحاجة.

## خطة تحقق تجاري خلال 14 يومًا

1. **اليوم 1–2:** مقابلة 5 ورش من أنواع مختلفة، وتوثيق كيف تسعّر العمل، وكيف تحصل على الموافقة، وكيف تعرف ربح أمر الشغل.
2. **اليوم 3–4:** عرض نموذج مبسط للوحة ربحية وموافقة العميل؛ لا نعد بتكاملات غير جاهزة.
3. **اليوم 5–7:** اختيار ورشة واحدة كتجربة تصميم، واستخدام بيانات تجريبية أو منزوعة الهوية حتى تُعتمد الحماية.
4. **اليوم 8–10:** قياس خط أساس يدوي: زمن إعداد العرض، نسبة البنود غير المعتمدة، الفروقات بين القطع المصروفة والمفوترة، ونسبة عودة العملاء إذا كانت البيانات متاحة.
5. **اليوم 11–14:** عرض سعر تجريبي واضح وجمع قرار شراء أو التزام تجربة مكتوب. لا نعتبر المجاملات أو التسجيلات المجانية دليلًا على الاستعداد للدفع.

**بوابة قرار:** إذا لم تستطع الورشة إثبات قيمة مالية من المؤشر أو لم ترغب بالدفع بعد التجربة، نعدّل الفرضية قبل توسيع البرمجة.

## ما لا نفعله الآن
- لا نعد بتشخيص آلي موثوق للأعطال.
- لا نعلن تكامل ZATCA أو WhatsApp أو أجهزة فحص قبل تنفيذه واختباره.
- لا نضيف microservices أو نغيّر Supabase production لتسهيل الاختبارات.
- لا نعيد بناء العملاء/المركبات/الحجوزات/أوامر العمل الموجودة.
- لا ندمج هذا التوثيق أو أي تغيير في `main` قبل مراجعة الـPR وبوابات CI المطلوبة.
