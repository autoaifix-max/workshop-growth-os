# إعداد أول ورشة ومالكها — إجراء تشغيلي لمرة واحدة

هذا إجراء يدوي لمشغّل موثوق فقط. لا يضيف مسار تسجيل ورشة عامًا، ولا يُشغّل تلقائيًا أثناء CI أو النشر. لا تستخدمه على الإنتاج قبل اعتماد قرار الإطلاق صراحةً؛ استخدم مشروع تطوير/اختبار منفصلًا أولًا.

## المتطلبات قبل التنفيذ

1. تأكد من مرجع مشروع Supabase المقصود في لوحة المشروع وإعدادات الاستضافة. توقف إذا كان الهدف غير واضح.
2. تأكد أن الترحيلات المطلوبة مطبقة مسبقًا. لا تطبق ترحيلات أثناء إنشاء الورشة.
3. أنشئ/ادعُ المالك من **Supabase Authentication → Users**. لا تُدخل المستخدم مباشرة في `auth.users`.
4. تأكد من إعداد رابط إعادة التوجيه في Supabase Auth ليسمح بـ `https://workshop-growth-os.netlify.app/auth/callback`، واستخدمه كرابط دعوة. بعد الدعوة، يجب أن ينتقل المستخدم إلى `/set-password` لتعيين كلمة المرور.
5. لا تضع مفتاح `service_role` في المتصفح أو ردود API أو مستودع Git.
6. اختر بريد حساب المالك الحالي، واسم الورشة، وslug فريدًا. لا تُدخل بريدًا لم تتم دعوته/إنشاؤه مسبقًا.

## الخطوة 1: تحقق للقراءة فقط

استبدل البريد الإلكتروني وslug في الاستعلام أدناه بالقيم المقصودة، وشغّله داخل SQL Editor بعد التحقق من مرجع المشروع:

```sql
select
  u.id as owner_user_id,
  u.email as owner_email,
  exists (
    select 1 from public.workshops w
    where lower(w.slug) = lower('replace-with-unique-slug')
  ) as slug_already_exists,
  exists (
    select 1 from public.workshop_memberships m
    where m.user_id = u.id and m.status = 'active'
  ) as already_has_active_membership
from auth.users u
where lower(u.email) = lower('REPLACE WITH OWNER EMAIL');
```

لا تستمر إلا إذا أعاد الاستعلام صفًا واحدًا بالضبط، وكان `slug_already_exists = false` و`already_has_active_membership = false`. إذا اختلفت النتيجة، توقف وافحص الحالة يدويًا.

## الخطوة 2: تهيئة الورشة

استخدم **السكربت الوحيد المعتمد**:

`supabase/operations/bootstrap-first-workshop.sql`

استبدل ثلاثة عناصر فقط: بريد المالك، اسم الورشة، وslug الورشة. راجع القيم، وأعد تحقق القراءة فقط، ثم تأكد مرة أخيرة من أن SQL Editor متصل بمشروع Supabase الصحيح قبل التنفيذ.

يتحقق السكربت من وجود مستخدم Auth واحد مطابق للبريد، ومن صلاحية الـ slug وعدم تكراره، ويرفض التنفيذ إذا كان للمستخدم أي اشتراك فعّال سابق. ثم ينشئ الورشة وعضوية المالك بدور `owner` داخل معاملة واحدة. إذا فشل إدخال العضوية، تُلغى العملية كلها.

الملف خارج مجلد `supabase/migrations`، ولا ينفذ تلقائيًا في CI أو النشر. إذا ظهر خطأ أو كانت النتيجة غير واضحة، افحص البيانات الناتجة قبل إعادة المحاولة؛ لا تُعد تشغيل السكربت بشكل أعمى.

## التحقق بعد التنفيذ

1. استعلم بصورة مستقلة عن الورشة والعضوية والبريد للتأكد من وجود نتيجة واحدة مطابقة للمالك المقصود.
2. سجّل الدخول بصفحة التطبيق، وأكمل قبول الدعوة وتعيين كلمة المرور.
3. تحقق أن النظام يستخرج `workshop_id` من عضوية المستخدم الفعالة، ولا يقبل معرّف الورشة المرسل من المتصفح كمرجع للصلاحية.
4. تحقق أن الحساب دون عضوية فعالة يُرفض، وأن الحساب المرتبط بأكثر من ورشة يتلقى استجابة اختيار الورشة.
5. نفّذ رحلة العميل ← المركبة ← الحجز ← أمر العمل في بيئة اختبار معزولة.
6. نفّذ اختبارات عزل الورش وتأكد من رفض القراءة والكتابة عبر حدود الورش.
7. وثّق البيئة ورابط CI والنتائج. نجاح الاختبارات الوهمية أو ظهور صفوف في قاعدة البيانات لا يثبت وحده نجاح الرحلة الحية.

## حدود الإجراء

- لا توجد نقطة تهيئة عامة أو تسجيل ذاتي.
- لا يتضمن هذا الدليل تنفيذًا على الإنتاج أو أي تغيير في قاعدة البيانات.
- لا تُضعف سياسات RLS ولا تتجاوز الصلاحيات ولا تكشف مفاتيح سرية.
- وجود هذا الملف لا يعني أن ورشة فعلية قد أُنشئت.
