# إعداد أول ورشة ومالكها — إجراء تشغيلي لمرة واحدة

هذا الإجراء مقصود أن ينفذه مشغّل موثوق يدويًا، وليس عبر endpoint عام. لا تضف مسار تسجيل ورشة غير محمي، ولا تضع مفتاح Supabase service-role في المتصفح أو في رد API.

## المتطلبات قبل التنفيذ
1. تأكد أن migrations الأساسية الخاصة بـ `workshops` و`workshop_memberships` مطبقة على مشروع Supabase المستهدف.
2. أنشئ حساب المستخدم المقصود من خلال Supabase Auth، أو تأكد أن الحساب موجود بالفعل.
3. من لوحة Supabase Auth، انسخ **UUID** للمستخدم المقصود. لا تستخدم البريد الإلكتروني بدل UUID.
4. تأكد أن المستخدم ليس لديه عضوية ورشة فعالة. إذا كان لديه عضوية، توقف وراجع الحالة يدويًا بدل إنشاء عضوية ثانية.
5. اختر اسم الورشة وslug فريدًا صالحًا (أحرف إنجليزية صغيرة وأرقام وشرطات).

## التنفيذ
1. افتح SQL Editor في مشروع Supabase الصحيح، وتأكد من اسم المشروع قبل تشغيل أي SQL.
2. افتح `supabase/operations/bootstrap-first-workshop.sql`.
3. استبدل `target_user_id` و`workshop_name` و`workshop_slug` بالقيم المقصودة. السكربت يرفض القيم الافتراضية.
4. راجع الاستعلام كاملًا، ثم نفذه مرة واحدة.
5. إذا ظهر أي استثناء، لا تعاود المحاولة بشكل أعمى؛ عالج السبب أولًا.
6. نفذ استعلام التحقق الموجود في نهاية السكربت بعد استبدال slug بالقيمة النهائية، وتأكد من ظهور ورشة واحدة وعضوية واحدة بدور `owner` وحالة `active`.

## الضمانات والحدود
- العملية داخل كتلة PostgreSQL واحدة؛ فشل إدخال العضوية يُفشل العملية كلها.
- يتحقق السكربت من وجود المستخدم، وعدم وجود عضوية فعالة سابقة، وعدم استخدام slug موجود.
- السكربت خارج مجلد migrations ولا يعمل تلقائيًا في CI أو عند النشر.
- لا يمنح المستخدم صلاحية إدارة عامة للمشروع؛ يضيف فقط عضوية مالك للورشة المنشأة.
- لا ترسل مفاتيح سرية أو بيانات مستخدمين إلى المحادثات أو سجلات CI.
- بعد الإعداد، اختبر مسارات API بمستخدم مسجل الدخول. وجود الصفوف في قاعدة البيانات وحده لا يثبت أن رحلة التطبيق كاملة تعمل.

## الاسترجاع
لا تحذف الورشة أو العضوية آليًا عند الفشل. افحص الصفوف الناتجة أولًا، ثم نفذ أي تصحيح يدوي بعد التأكد من أن الورشة لا تحتوي بيانات تشغيلية.
