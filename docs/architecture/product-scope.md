# نطاق المنتج — Workshop Growth OS

## الرؤية
منصة SaaS عربية لإدارة وتشغيل ورش صيانة السيارات، تساعد الورشة على تحويل استفسار العميل إلى أمر عمل قابل للتتبع، وتشخيص موثق، وموافقة واضحة، وإصلاح وفحص جودة، ثم فاتورة وتحصيل وقياس للربحية والعودة المستقبلية للعميل.

## المستخدمون
- مالك المنصة: إدارة الخطط والاشتراكات وتفعيل الورش ومراقبة صحة الخدمة دون الاطلاع غير المبرر على بيانات الورش.
- مالك/مدير الورشة: الإعدادات والفريق والخدمات والأسعار والتقارير.
- موظف الاستقبال: العملاء والسيارات والمواعيد والاستلام والتواصل.
- الفني: التشخيص والعمل والقطع المستخدمة والفحوص والأدلة.
- المحاسب/المشرف المالي: الفواتير والتحصيل والتسويات والتقارير المسموح بها.
- العميل: عرض تقدير الأعمال والموافقة، ومتابعة حالة السيارة والمستندات المسموح نشرها.
- الشريك/المسوّق المُحال: لا يحصل إلا على بيانات الإحالة والعمولة المصرح بها، إن فُعّلت الوحدة.

## النطاق الوظيفي
1. حساب الورشة والفريق والأدوار وسجل التدقيق.
2. العملاء والسيارات وسجل الزيارات.
3. استقبال السيارة والحجوزات وأوامر العمل ودورة الحالات.
4. تقديرات الأسعار والموافقة الموثقة قبل تنفيذ الأعمال الإضافية.
5. التشخيص: الأعراض، DTC، القراءات، الصور/المرفقات، نتائج الاختبار، السبب المرجح، والإجراء الموصى به.
6. خطوات الفني، القطع والأجور، فحص الجودة، التسليم والضمان عند تحديد السياسة.
7. الفواتير والضريبة والخصومات والتحصيل والرصيد والربحية؛ لا تُعد القيود المحاسبية بديلًا عن مراجعة محاسبية نظامية.
8. ملفات ومستندات خاصة وروابط تنزيل مؤقتة.
9. تذكيرات ومتابعات وتسويق فقط وفق أساس نظامي وموافقة العميل والقنوات المصرح بها.
10. إدارة اشتراكات المنصة والخطط وحالة الدفع وحدود الميزات.
11. الإحالات والعمولات: احتسابها على خدمات مؤهلة ومحصلة، مع قواعد منع التكرار والإلغاء والاسترداد والتسوية والتدقيق.
12. استيراد تقارير أجهزة الفحص مثل Autel وLAUNCH من ملفات أو صيغ موثقة. لا يُفترض وجود تكامل مباشر مع الجهاز أو API تجاري قبل التحقق من دعم المورد وشروطه.
13. وحدة معرفة وتشخيص ذكية تُظهر مصادرها وحدود الثقة ولا تستبدل قرار الفني.
14. تقارير تشغيلية ومالية حسب صلاحية المستخدم.

## مبادئ المنتج
- العربية وRTL أولًا، وتجربة متجاوبة للجوال داخل الورشة.
- بناء قابل للتوسع من ورشة واحدة إلى عدة ورش مع عزل tenant مفروض على الخادم وقاعدة البيانات.
- API بإصدار `/api/v1`، ومنطق الأعمال مستقل عن مكونات الواجهة.
- الاستعداد لتطبيق Android ثم iPhone من خلال عقود API مستقرة، ومصادقة مناسبة للجوال، ورفع ملفات آمن، وإشعارات قابلة للتوسعة. لا يُحسم PWA أو React Native أو Flutter قبل التحقق من الحاجة والأصول والتكلفة.
- استخدام مصدر حقيقة واحد لكل مجال. لا ننشئ Runtime أو Router أو Database أو Auth مكررًا.
- كل تغيير مالي أو تغيير صلاحية أو قرار موافقة يجب أن يكون قابلًا للتدقيق.
- لا تُعرض وظيفة على أنها مكتملة حتى تُختبر من طرف إلى طرف.

## خارج الإصدار الأول
- تكاملات أجهزة مباشرة غير موثقة.
- إرسال WhatsApp تلقائيًا أو قراءة المحادثات دون إعداد رسمي وموافقات وصلاحيات واضحة.
- محاسبة نظامية شاملة أو تكامل ضريبي لم يُحدد متطلبه.
- تطبيقات جوال أصلية قبل ثبات API واختبار الاستخدام الفعلي.
- تشخيص آلي يتخذ قرار إصلاح أو سلامة دون اعتماد فني بشري.

## معايير نجاح الإصدار الأول
- تستطيع ورشتان تجريبيتان استخدام النظام دون رؤية بيانات بعضهما.
- دورة العميل/السيارة/أمر العمل/التشخيص/الموافقة/الجودة/الفاتورة تعمل عبر API والواجهة.
- لا يمكن تنفيذ عمل إضافي بلا موافقة حسب سياسة الورشة.
- لا يتكرر التحصيل أو احتساب العمولة عند إعادة الطلب.
- تنجح اختبارات الصلاحيات والعزل والتدفق، والبناء والفحوص الثابتة.
